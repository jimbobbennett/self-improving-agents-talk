# Self-Improving Thanksgiving Agent: Implementation Plan

## Goal

Build a reproducible demo loop that takes the existing Thanksgiving agent from `original/`, uses the Arize AX trace dataset and its evaluators to measure the baseline, asks a Codex-powered improvement agent for code changes, and accepts changes only when quality improves without unacceptable cost or latency regressions. The loop should end with a reviewable draft pull request containing the chosen change, experiment history, and an experiment screenshot.

## Current inputs

- Candidate application: `original/` (the committed baseline Thanksgiving chatbot and its search tool).
- AX space/project: `jbennett Space` / `thanksgiving-food-lore-demo`.
- Dataset: `thanksgiving-food-lore-traces-v1`, version `RGF0YXNldFZlcnNpb246NDAyNjcxOi9FTzY=`, with 117 examples. The local snapshot is `evals/thanksgiving-trace-dataset.json`.
- Five evaluator definitions exist in AX. The online task configuration is recorded in `evals/ax-task-config.json`; tool-contract and search-selection are continuously scored, with three quality judges run as a backfill to control cost.
- `evals/ax-evaluators.json` records evaluator IDs and the tool-contract check; use the task/evaluator configuration as the source of truth and fail clearly if required evaluators are unavailable.

## Architecture

Add an isolated `improver/` TypeScript CLI package using the official `@openai/codex-sdk` (`Codex`, `startThread()`, `thread.run()`)—distinct from the Thanksgiving app's existing `@openai/agents` package. Its bounded Codex threads inspect experiment evidence and propose candidate patches inside isolated worktrees. Deterministic TypeScript code owns dataset loading, candidate isolation, AX experiment creation/execution, score extraction, guardrails, stopping, report generation, and GitHub PR creation. The model must not invent experiment results or directly choose a winner without the deterministic score gate.

Each candidate is a separate git worktree based on the current best accepted candidate. It receives only one proposed change at a time. Evaluation runs against the same frozen dataset version and evaluator set for every candidate. Candidate code must use the original app implementation and real configured model/tools; fabricated model answers, evaluator labels, costs, or timings are forbidden. A failed run is recorded as a failed candidate, not silently retried into a pass.

## Workflow

1. **Preflight:** verify required environment configuration without printing secrets; verify the `@openai/codex-sdk` package and usable Codex CLI/authenticated session, `ax` CLI, dataset, project, evaluator IDs, writable working tree, and GitHub CLI availability. Validate unique dataset row IDs, required input fields, all row mappings, local judge template placeholders and output labels, provider credentials, and experiment create/export/annotation joins using a no-spend fixture. Ensure the five categorical annotation configs exist before paid agent calls. Exit before paid calls if a check fails. Default to one iteration and require a user-set spend ceiling; require explicit confirmation before a full dataset run whose projected spend exceeds the configured threshold.
2. **Load and freeze data:** export the exact AX dataset version (or verify the checked-in snapshot matches it); normalize each example into its user prompt and any supported context/expected labels. Preserve source trace IDs and evaluator labels for audit. Never treat old labels as the candidate's new evaluation result.
3. **Baseline:** record the original agent source revision as the baseline. Call the Thanksgiving agent directly from the candidate checkout (the app's `runPlanner()` and its real configured model/tools), once per dataset prompt. The Codex SDK is only the code-improvement agent; it does not generate candidate Thanksgiving answers. Capture outputs, raw tool inputs/outputs/errors, search evidence, token usage, tool-call count, and end-to-end latency. `runPlanner()` returns structured per-tool evidence and counters; the local judge context is serialized with `JSON.stringify(searchEvidence)` to match the AX trace attribute representation and preserve evidence ordering. Clearly identify this as a fresh run (snapshot outputs/labels are audit references only). Upload those actual candidate runs as a named AX experiment linked to the frozen dataset version. Record AX experiment/run IDs and links.
4. **Generate three candidates:** give Codex the baseline traces, per-evaluator outcomes, and a concise failure analysis. Ask for exactly three distinct, small, independently applicable fixes. Require each proposal to state its target failure, expected evaluator impact, likely cost/latency impact, and files to change.
5. **Evaluate candidates separately:** make one isolated worktree and one named AX experiment per proposal; run the same dataset and model/tool settings. Reject invalid patches or runs that cannot be reproduced. Preserve each example's search evidence and raw tool-call inputs. Run the four LLM judges locally against the final output and captured evidence, using version-controlled replicas of AX prompts, labels, explanation fields, structured function-call output, and serialized context format. Calibrate against stored AX labels and explanations without tuning prompts to the same historical labels. Current calibration is not yet sufficient to treat local and historical AX labels as interchangeable; report that limitation and investigate variance before using scores to rank candidates. Run Tool Contract locally as a deterministic check over each raw tool input. The AX task smoke test did score three experiment rows, but experiment scoring will remain local for this demo. Save per-example scores, explanations, prompt hashes/versions, model ID, and inputs as local artifacts; identify them as local scores, never AX task scores. Attach local results to AX experiment run IDs using categorical labels and explanation text (do not send a numeric score for categorical configs). Mark no-tool cases N/A; report applicability, invalid attempts, and final query pass separately. Any invalid attempt fails this evaluator even if a retry later succeeds. Each quality judge is scored once per query.
6. **Select top two:** apply deterministic eligibility gates first. Candidate must pass minimum quality floors and improve the targeted issue; allow a one-example drop per evaluator to absorb borderline judge variation, but reject larger drops. Keep mean cost and p95 latency at or below 110% of both the fixed baseline and current best. Rank eligible candidates by the macro-average of the four trace-level evaluator pass rates (Factual Grounding, Dish Classification, Source Integrity, Search Selection Bias), while reporting Tool Contract separately as query-level pass rate (a query passes only if every attempted tool call is valid). Require an aggregate gain larger than one-evaluator/one-example score resolution (`1 / (4 * example_count)`). Treat historical Dish Classification pass rates as weak coverage evidence until the dataset has more failure examples. Tie-break by lower cost, then lower latency. If fewer than two qualify, continue with the best eligible one; if none qualify, stop and report no accepted improvement.
7. **Breed next iteration:** pass the two top candidate diffs and their measured outcomes to Codex, along with the best-so-far version. Request three new distinct proposals that combine or refine observed successful ideas without changing evaluation data or evaluator definitions. Evaluate and rank them as above. The best candidate becomes the new best only when it passes all gates and strictly improves the objective.
8. **Stop:** default to one improvement iteration; stop when a complete iteration produces no qualifying strict improvement, or at configurable maximum iteration/candidate/API-spend budgets. Account for failed and timed-out requests in latency/cost summaries; never silently drop them. If provider token pricing is unavailable, mark monetary model cost unknown and fail closed for the cost gate unless the user explicitly permits token-only comparison. The fixture's `estimated_external_cost_usd` is simulated and must never be represented as real cost. Keep the best eligible version and stop candidate generation after any stop condition.
9. **Report and PR:** generate a detailed Markdown report with baseline and candidate versions, patch summaries, per-evaluator scores, aggregate score, mean cost, p95 latency, tool-call counts, AX experiment links, guardrail outcomes, accepted/rejected reasons, stopping reason, and dataset/evaluator versions. Capture a screenshot of the best experiment only through an authenticated browser automation or supported AX export, and verify it depicts the cited experiment; if screenshot capture is unavailable, stop before PR creation and clearly report the missing artifact. Create a draft PR from a clean branch based on `main` containing only the selected best patch and report artifacts; do not include unrelated pending dataset/eval changes. Never merge or publish automatically.

## Metrics and guardrails

- **Quality:** report every evaluator separately (Factual Grounding, Dish Classification, Source Integrity, Search Selection Bias, and Tool Contract). The composite score is the macro-average of pass rates, calculated only over applicable examples/spans. Allow at most one additional failing example per evaluator versus current best to accommodate judge variance; reject larger regressions and require a strict aggregate or targeted-evaluator improvement.
- **Cost:** compare mean estimated model cost per example, derived from actual token usage and an explicit model price table; distinguish estimates from provider-billed amounts. Report tool-call count and known external tool costs separately. Fixture external costs and artificial delays are simulated; never use them as actual metrics. Verify `runPlanner()` exposes provider token usage or collect it reliably from SDK traces; otherwise cost is unknown and blocks acceptance. Include Thanksgiving calls, local judges, Codex proposals, and retries in the spend ceiling. At 117 rows, baseline plus three candidates means up to 468 agent runs and 1,872 judge calls per iteration before retries and Codex calls; display this projection before launch.
- **Latency:** compare p95 end-to-end example latency, with consistent timeout and retry policy. Enforce the 10% ceiling against baseline and current best. Include failures/timeouts in summaries and treat missing measurements or excessive failures as ineligible.
- **Budgets:** defaults are one iteration, three proposals, concurrency of two agent runs and two judge calls, one bounded transport retry (recorded in cost/latency), and an explicit spend limit. A smoke run validates wiring but cannot select winners; only full-dataset results can accept a candidate. Display projected calls and require explicit full-run consent when the configured threshold applies.

## AX experiment and local evaluation implementation

Run the candidate agent directly on each example, then create a dataset-versioned AX experiment from those real outputs and tool evidence. Keep one-to-one run/example mapping using the top-level exported dataset row `id` as `example_id`; never use `source_trace_id`. Existing outputs and labels are reference material only. Compute candidate scores locally: four LLM judges once per example and deterministic Tool Contract over raw tool inputs. Mirror AX prompts and rules in version-controlled local evaluator definitions; first export active AX versions and compare templates, labels, and score normalization. Until verified, call these local replicas rather than AX evaluators. Record prompt hash/version, judge model/settings, evidence passed to each judge, raw response, and normalized score. Calibrate against a small fixed set of previously scored examples and report agreement/confusion without tuning against those historical labels. Pass each judge only the candidate's captured tool evidence/source metadata, with a deterministic empty-context representation; keep historic dataset context separate for audit. Preserve tool evidence across failed and corrected calls, and verify AX experiment metadata limits do not truncate it. Validate local output schema and bounded retries. AX project tasks continue to score live traces; do not mix those scores with local candidate scores. For optional AX visibility, export the experiment to obtain AX run IDs, join by stable `example_id`, and attach local results to those run IDs with clear local-evaluation labels. If annotation is unsupported, retain local results and link them from the manifest. Mark no-tool cases N/A; report applicability, invalid attempts, and final query pass separately. Any invalid attempt fails Tool Contract even if a later retry succeeds. Record AX experiment IDs separately from local evaluation run IDs.

Every experiment name includes run timestamp, iteration, and variant (baseline or candidate label). Store a machine-readable manifest for all runs with dataset version, evaluator IDs/versions, code revision, model configuration, AX identifiers, metrics, and artifacts.

## PR/report artifacts

- Selected patch on a named branch and a **draft** PR only.
- `reports/<run-id>/report.md` with experiment table, iteration narrative, detailed evaluator/cost/latency data, links, and recommendation.
- `reports/<run-id>/manifest.json` for reproducibility.
- `reports/<run-id>/best-experiment.png` screenshot tied to the AX best experiment, with capture source/time documented.
- PR body summarizes the improvement and guardrail checks, and links to the full report and AX experiments.

## Safety, reproducibility, and demo controls

- Default to dry-run until explicit run flags are supplied; show projected candidate count and example count before paid work.
- Use bounded Codex turns, strict JSON schemas for proposals, explicit subprocess timeouts, and hard iteration/spend ceilings.
- Keep credentials in environment/configured CLI profiles only; never serialize secrets into reports, logs, prompts, or PR artifacts.
- Pin the AX dataset version and evaluator versions for an entire run. Record every prompt/model/tool config so reruns are comparable.
- Preserve the `original/` baseline unchanged; all generated patches and experiments happen in isolated worktrees.
- PR creation is draft-only; the loop must stop after opening it and print the review link.
